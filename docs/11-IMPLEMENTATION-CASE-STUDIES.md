# 具体的な設計手法のケーススタディ（初回調査 2026-11-11）

README紹介に留めず、公開された**実装参照文書・変更履歴・開発記録**を確認。IronAsiaがどう工夫を取り込むかと、どの点が未実証かを分ける。第三者コードのコピーは行わない。

## Case A: Millennium Dawnの国際連合 — 状態機械と故障復旧
**参照**: [UN system reference](https://github.com/MillenniumDawn/Millennium-Dawn/blob/main/.claude/docs/un-system-reference.md) ／ [開発者向け国際システム解説](https://github.com/MillenniumDawn/Millennium-Dawn/blob/main/docs/src/content/tutorials/international-systems.md)

- **確認した実装構成（SOURCE CODE REFERENCE DOC）**: common/scripted_effects、events、decisions、triggers、scripted_guis、on_actionsに分散。投票要求→同時処理制限と待ち行列→投票開始→採決→効果・通知→後片付け、という状態機械。
- **強み**: 総会と安保理の投票種別を別の名前空間で扱い、採決成立に必要な人数を適格者から再計算。投票対象国は安全保障理事会の対象議決から除外。ある時点の結果は、その時点の状況を保持した受け手側の変数で扱う。
- **重要な失敗例**: 投票途中で任務担当国が併合・消滅すると採決が永遠に終わらなくなる。現在進行中の投票、投票待ち、脱退国参照、遅れて届く投票UI、拒否権の残骸を適切に消す必要がある。中止の入口を専用処理にまとめ、定期点検で詰まりを回復。
- **IronAsiaに応用**: 「国境紛争ケース」も、申立→仲裁準備→係争→妥協/制裁/武力化→終結の状態機械とし、当事国消滅・戦争・政体変更・期限切れで必ず状態を片付ける。**単一の権威ある終結関数とケース重複防止**を候補にする。
- **採用しないもの**: 現代の国連安保理・拒否権を1936年の国際連盟へそのまま移植すること。歴史的制度/加盟/権限の初期条件は別途一次資料で裏付ける。
- **残タスク**: 実際のスクリプト参照を追跡し、状態遷移のテスト手順を構築する。IronAsiaで同一実装が可能とは未認定。

## Case B: Millennium Dawnの高速化 — 世界計算は頻度と重複が支配する
**参照**: [Dev Diary #54 / 2026-03-09](https://github.com/MillenniumDawn/Millennium-Dawn/blob/main/docs/src/content/devDiaries/054-performance-of-the-md-beta.mdx)

- **確認（作者の実測主張）**: 同一CPUとGPUでOS変更も含む比較にて、daily tick平均219→72ms、weekly 404→113ms、monthly 445→212ms。ハード/OSが完全一致しないのでIronAsiaへの効果保証ではない。
- **具体的工夫**: 数値の丸め/正規化の複雑な補助コードを整理、動的modifierの再計算を統合、死んだ仕組み/ログ/重複コードを除去。power rankingは半年ごと、変化の遅いEU等の計算は月次へ移行し、週次更新を必要としない再生可能エネルギー処理を簡略化。
- **IronAsiaに応用**: 国家間関係の全ペア全日更新をやめ、重要事件発生時の差分更新+月次の案件評価へ。将軍/研究の再評価も常時ではなく必要時/分散更新を候補とする。
- **監査**: 決して更新間隔だけを延長して史実因果を失わない。危機の期限とゲーム内応答が成立するか測定する。
- **教訓**: 「全コードを0から書く」ことより、**更新頻度/データモデルの一貫性と不要な仕組みの削減**が性能に効く可能性が高い。ゼロから再設計するなら、古い複雑さを再輸入しない。

## Case C: Tech Baseline Mechanics — 小国の研究救済と計算分散
**参照**: [README](https://github.com/henri14871/hoi4-tech-baseline-mechanics), [scoring API](https://github.com/henri14871/hoi4-tech-baseline-mechanics/blob/main/SCORING_API.md)

- **確認（作者説明）**: 経済、科学、動員、資源、戦時状態の5次元で国力を評価し、6段階の能力階層を設ける。陸海空/産業4分野の独立した適性、前線や軍事援助・同盟・戦時の追いつきを組み合わせる。評価を月の複数バケットへ分散し、階層が頻繁に上下しないためのヒステリシスも使用。
- **興味深い点**: 小国にも「何でも研究できる」権利を無条件に付与せず、**必要技術の底上げ**と**得意分野の差**を両立。作者はAI国デフォルト・プレイヤー研究は触らないと明記。
- **IronAsiaに応用**: 研究自動化を「選択UIの省力化」と「技術格差救済」に分割。小国は進歩が止まりにくく、大国が全分野で即座に完成することは避ける。
- **採用しないもの**: 現行の6段階の定数、技術自動付与の量をそのまま流用すること。小国の強さは別途均衡実験で決める。
- **未検証**: 作者は対象版HOI4 1.17.5.2と明記。現行ユーザー環境では版互換を実測し、プレイヤー研究枠の自動運用とは別に扱う。

## Case D: Millennium DawnのAIの操作負担低減と抑制
**参照**: [Changelog](https://github.com/MillenniumDawn/Millennium-Dawn/blob/main/Changelog.txt)
- **確認した変更履歴の例**: 影響力AIはプレイヤーと同系統の自動スロットを利用し、目標を一定期間維持。外交目的、相手との力関係、国際組織の共通性で対象を重み付け。無駄な再ターゲットや際限ない使い込みを防ぐ。
- **自動化の例**: 産業組織（MIO）の一定条件下の自動アンロックは、費用（政治力等）を支払い、予備資源を残す。税の自動化は定期見直しであり、操作なしで無制限の財源を生むものではない。
- **IronAsiaに応用**: 自動研究・艦船設計・外交AIには「利用予算」「維持する最低残高」「切替時の所有権」「再選択頻度」「意思決定理由」を設定可能にする。
- **採用しないもの**: 自動化をゲームルール固定の一括オン/オフだけにすること。可能な場合はプレイ中に部門単位で切替たい（実装可能か要検証）。

## Case E: 地図設計とツール — Province増加の連鎖
**参照**: [Map modding](https://github.com/thelight0211/hoi4-wiki/blob/main/Map%20modding%20-%20Hearts%20of%20Iron%204%20Wiki.md), [HOI4 Map Editor](https://github.com/AdriianCOE/HOI4-Map-Editor), [Historical States](https://steamcommunity.com/sharedfiles/filedetails/?id=3129639972)

- **確認（地図仕様）**: provinces.bmpの識別色、definition.csvのID/地形/海岸、州、補給ノード・鉄道、戦略地域とそれらへの参照を維持する必要がある。画像形式やビット深度の間違いも起動失敗の原因となる。
- **IronAsiaに応用**: アフリカ/中国の国境・地形・都市・補給・戦略の精度が必要な場所から増設。province数そのものではなく、歴史再現/戦闘への寄与と性能負担で評価する。
- **未確認**: 他MODの地図データを再配布する権利、現行ゲーム版への互換性、既存セーブ互換。これらがないまま導入しない。

## 使い方
実装着手時は全件を読み込まない。課題別に1～2件だけ参照して「出典→具体的パターン→代案→POC」を最小限で繰り返す。すべての提案はIronAsiaの体験目標に従属し、ツールや外部MODの採用そのものを目的にしない。
